# 三色标记算法

在 Go 语言语境里，“三色标记算法”通常指垃圾回收器用来判断对象是否存活的算法。

它不是对象真的有颜色，而是用三种状态表示对象是否被扫描。

#### 三种颜色

* 白色：还没有被垃圾回收器访问
* 灰色：已经发现对象存活，但它引用的其他对象还没有扫描完成
* 黑色：对象存活，并且它引用的对象也已经扫描完成

垃圾回收开始时，堆里的对象通常都看作白色。

#### 标记过程

假设对象关系是：

```
Root → A → B → C

       D
```

`Root` 表示 GC Root，例如：

* 全局变量
* 当前 goroutine 栈上的局部变量
* 寄存器里的指针
* runtime 内部持有的对象

开始时：

```
A、B、C、D 都是白色
```

从 Root 开始扫描，发现 `A`：

```
A：灰色
B、C、D：白色
```

扫描 `A`，发现它引用了 `B`：

```
A：黑色
B：灰色
C、D：白色
```

扫描 `B`，发现它引用了 `C`：

```
A、B：黑色
C：灰色
D：白色
```

扫描 `C`：

```
A、B、C：黑色
D：白色
```

当没有灰色对象时，标记结束：

* 黑色对象：从 Root 可以到达，属于存活对象
* 白色对象：无法从 Root 到达，可以被回收

所以 `D` 会被回收。

#### 为什么需要灰色

灰色表示“已经知道它活着，但还没检查完”。

垃圾回收器可以维护一个灰色对象队列：

```
for 灰色队列不为空 {
    obj := 取出一个灰色对象

    for _, child := range obj引用的对象 {
        if child是白色 {
            将child标记为灰色
        }
    }

    将obj标记为黑色
}
```

这本质上是从 GC Root 开始进行图遍历。

#### 并发标记的问题

Go 的垃圾回收器会尽量和业务 goroutine 并发运行。

在 GC 扫描的同时，业务代码可能修改指针。例如原来：

```
黑色 A       白色 B
```

业务代码突然执行：

```
A.child = B
```

变成：

```
黑色 A → 白色 B
```

但 `A` 已经扫描完成，GC 可能不会再扫描它。如果没有额外措施，`B` 可能被错误地当成垃圾回收。

这就是三色标记算法中的关键风险：

```
黑色对象直接引用白色对象
```

#### 三色不变式

为了保证并发标记正确，需要维持某种不变式。

强三色不变式：

```
黑色对象不能直接引用白色对象
```

弱三色不变式：

```
如果黑色对象引用白色对象，
必须存在一条从灰色对象到该白色对象的可达路径
```

Go 通过写屏障来维持这些条件。

#### 写屏障

写屏障不是阻止写入，而是在修改指针时插入一小段额外逻辑。

例如业务代码：

```
a.child = b
```

在 GC 标记期间，概念上可能变成：

```
写屏障处理旧指针和新指针
a.child = b
```

写屏障会把可能被漏掉的对象标记为灰色，放进等待扫描的队列。

Go 使用的是混合写屏障，其思想可以简化为：

```
删除旧引用时：保护旧对象
添加新引用时：保护新对象
```

概念代码类似：

```
writePointer(slot, newPtr) {
    shade(*slot) // 旧指针指向的对象标灰
    shade(newPtr) // 新指针指向的对象标灰
    *slot = newPtr
}
```

实际实现会有更细致的条件和优化，不是每次都机械地执行上述全部操作。

#### Go GC 的大致阶段

1. 标记准备

短暂暂停所有 goroutine，也就是 STW。开启写屏障，确定扫描起点。

2. 并发标记

GC 与业务 goroutine 同时运行，从 GC Root 出发不断扫描灰色对象。

3. 标记终止

再次短暂 STW，完成剩余标记，然后关闭写屏障。

4. 清扫

回收仍然是白色的对象所占用的内存。清扫通常也可以并发进行。

一句话总结：

> 三色标记把对象分成未发现、待扫描和已扫描三种状态，从 GC Root 遍历对象引用图；Go 再通过写屏障解决并发修改指针导致的漏标问题。



#### 与JAVA的区别

原理层面基本相同，都是从 GC Root 出发，通过三色标记判断对象是否存活；但 Go 和 Java 的具体垃圾回收器实现差别很大。

| 对比项     | Go GC                  | Java GC                   |
| ------- | ---------------------- | ------------------------- |
| 基础思想    | 三色标记、可达性分析             | 三色标记、可达性分析                |
| GC Root | 栈、全局变量、寄存器、runtime 对象等 | 线程栈、静态变量、JNI 引用等          |
| 并发标记    | 支持                     | G1、ZGC、Shenandoah 等支持     |
| 写屏障     | 混合写屏障                  | 根据收集器使用不同屏障               |
| 分代      | 通常不分代                  | 大部分收集器采用分代                |
| 对象移动    | 通常不移动对象                | 很多收集器会移动、压缩对象             |
| 收集器选择   | runtime 内置统一 GC        | 可以选择 G1、ZGC、Parallel GC 等 |

共同点都是：

```
GC Root
   ↓
发现对象：白色 → 灰色
   ↓
扫描引用：灰色 → 黑色
   ↓
剩余白色对象被视为垃圾
```

主要区别在并发处理上。

Go 使用混合写屏障，主要防止业务 goroutine 修改引用时产生漏标：

```
旧引用被删除 → 保护旧对象
新引用被添加 → 保护新对象
```

Java 要看具体收集器。例如 G1 的并发标记主要采用 SATB，可以理解为“以标记开始时的对象关系快照为准”。删除引用时，通过写屏障保护旧引用指向的对象：

```
// 概念代码，不是真正的 Java 实现
old := object.field
shade(old)
object.field = newObject
```

Java 的很多 GC 还会整理内存并移动对象：

```
整理前：[存活][空闲][存活][空闲]
整理后：[存活][存活][    空闲    ]
```

因此 Java 还需要修正对象地址。Go GC 通常不会移动普通堆对象，减少了地址更新的复杂度，但可能产生一定的内存碎片。

所以更准确地说：

> Go 和 Java 使用相同的可达性分析、三色标记思想，但写屏障、分代策略、对象移动、内存整理和暂停控制方式取决于各自的垃圾回收器实现。Java 也不是只有一种 GC，因此不能把“Java GC”看成一个固定算法。
