# 为什么使用hazelcast

我们当时选择 Hazelcast 作为撮合系统的内存存储，主要是因为撮合系统需要同时满足低延迟、高并发、分布式状态共享、高可用和 Java 体系集成这几个要求。

撮合链路不能每次都访问数据库，否则数据库 IO 会成为瓶颈，所以核心订单状态、订单簿、撮合中间状态、部分账户或持仓状态需要放在内存里。Hazelcast 本质上是一个 In-Memory Data Grid，也就是分布式内存数据网格，它可以把数据放在 JVM 内存中，并且在多节点之间自动分区、同步和备份，比较适合交易系统这种对实时性要求很高的场景。

***

第一，Hazelcast 的读写延迟低。

撮合系统最核心的是性能。如果每笔下单、撤单、改单都查 MySQL，延迟和吞吐都很难满足要求。

Hazelcast 是内存级读写，数据直接在 JVM 内存里，访问延迟远低于数据库。对于订单状态、订单簿快照、撮合过程中的临时状态，可以直接从 Hazelcast 获取，减少数据库访问次数。

所以我们用 Hazelcast 承担实时状态层，MySQL 负责最终持久化，这样主链路更短。

***

第二，Hazelcast 支持分布式数据结构。

Hazelcast 不只是简单 KV，它提供了很多分布式数据结构，比如：

```
IMap
MultiMap
Ringbuffer
ReliableTopic
Queue
Lock
AtomicLong
```

在撮合系统里，IMap 可以用来存订单、订单状态、合约状态、用户状态等；MultiMap 可以用来表达一对多关系，比如价格档位下的多个订单；Ringbuffer 或 ReliableTopic 可以用来做内部事件通知或者消息分发。

这些数据结构本身就是分布式的，多个节点访问的是同一个逻辑数据结构，不需要我们自己实现状态同步。

***

第三，Hazelcast 支持自动分区和水平扩展。

Hazelcast 会把数据按照 key hash 到不同 partition。比如我们可以用 symbol、orderId、userId 作为 key，让数据分散到不同节点。

当集群节点增加时，Hazelcast 会自动做数据 re-balance；节点减少时，也会把数据迁移到其他节点。

对撮合系统来说，这个特性比较重要，因为交易对越来越多、订单量越来越大时，可以通过增加节点来扩容，不需要一开始就把所有状态都放在单机内存里。

***

第四，Hazelcast 支持主备副本，提高高可用能力。

撮合系统里的订单状态不能因为某个节点挂掉就丢失。Hazelcast 的 IMap 支持 backup，比如设置一个或多个 backup count。

一份数据会有主分区，同时在其他节点有备份。如果主节点挂了，backup 可以提升为新的主分区，继续提供服务。

这比单机本地内存更安全。单机 HashMap 性能虽然高，但进程挂了数据就没了；Hazelcast 至少可以通过副本机制降低单点风险。

***

第五，Hazelcast 对 Java 体系集成非常好。

我们的撮合系统本身是 Java / Spring Boot 技术栈，Hazelcast 也是 JVM 生态里的产品，和 Java 对象、Spring Boot、序列化机制、线程模型都比较容易集成。

相比单独引入一套外部缓存或状态服务，Hazelcast 嵌入式部署或者 Client-Server 模式都比较灵活。

尤其在撮合系统里，很多状态对象本身就是 Java 对象，使用 Hazelcast 存取会比自己做序列化、反序列化和状态同步更方便。

***

第六，Hazelcast 支持MapStore / MapLoader 持久化扩展。

Hazelcast 不能完全替代数据库，但它提供 MapStore、MapLoader 这类机制，可以把内存数据和外部数据库打通。

比如启动时可以从数据库加载订单状态到 Hazelcast；运行过程中可以把状态变更异步写回数据库。

这样就形成了：

```
Hazelcast 负责实时读写
MySQL 负责最终持久化
```

既能满足撮合性能，又能保证数据可恢复和可追溯。

***

第七，Hazelcast 支持事件监听和近实时通知。

Hazelcast 的 IMap 支持 EntryListener，可以监听数据新增、更新、删除事件。

在交易系统里，某些状态变化可以通过监听器触发后续处理，比如订单状态变更、缓存刷新、通知推送等。

这类能力可以减少我们自己写轮询逻辑，提升系统响应速度。

***

第八，Hazelcast 支持CP 子系统和分布式协调能力。

在一些需要强一致协调的场景，比如分布式锁、原子计数、选主、租约控制，可以使用 Hazelcast 的 CP Subsystem。

撮合系统里虽然核心撮合尽量避免依赖分布式锁，因为锁会影响性能，但在一些控制类场景，比如任务分配、状态切换、防止重复初始化，可以用分布式锁或者原子变量来保证安全。

也就是说，Hazelcast 不只是缓存，还能提供一定的分布式协调能力。

***

第九，Hazelcast 相比 Redis 的优势。

Redis 很适合做集中式缓存、排行榜、分布式锁、简单 KV 和消息通知，但在我们的场景里，Hazelcast 有几个优势：

第一，Hazelcast 是分布式内存数据网格，天然支持多节点数据分区和对象共享；Redis 如果要做分片，需要依赖 Redis Cluster，数据结构和 Java 对象模型没有 Hazelcast 这么贴近。

第二，Hazelcast 和 Java 对象集成更自然，撮合状态可以直接以对象形式组织，开发成本低。

第三，Hazelcast 支持 IMap、MultiMap、Ringbuffer、ReliableTopic 等更丰富的分布式结构，不只是简单 KV。

第四，Hazelcast 可以嵌入 Java 进程，也可以独立集群部署，部署模式更灵活。

所以 Redis 更适合作为行情缓存、热点缓存、排行榜、分布式锁等；Hazelcast 更适合做撮合内部的分布式内存状态层。

***

第十，Hazelcast 相比本地内存 HashMap 的优势。

如果只用本地 HashMap，性能确实最好，但问题是它不具备分布式能力。

比如进程重启后数据丢失；多节点之间状态无法共享；扩容后需要自己做数据迁移；故障恢复也要自己实现。

Hazelcast 在保留内存读写优势的同时，提供了分布式分区、副本、集群成员管理和数据迁移能力。

所以它比本地 HashMap 更适合多实例撮合系统。

***

第十一，Hazelcast 在架构里的定位。

我不会把 Hazelcast 理解成数据库替代品，而是把它定位成撮合系统的实时状态层。

我们整体架构是：

```
Kafka / MQ：负责订单事件输入和系统解耦
Hazelcast：负责撮合相关实时状态和低延迟读写
MySQL：负责最终持久化和对账追溯
Redis：负责行情缓存、深度缓存和推送辅助
```

撮合主链路尽量走 Hazelcast 和内存订单簿，避免频繁访问数据库；撮合完成后再通过 TradeService 批量落库，并更新分布式状态。

***

最后可以这样总结：

所以选择 Hazelcast 的原因不是单纯因为它是缓存，而是因为它同时覆盖了几个撮合系统需要的技术优势：

第一，内存读写，延迟低；第二，IMap、MultiMap 等分布式数据结构适合存订单和状态；第三，自动分区，方便按合约、订单或用户维度水平扩展；第四，backup 副本机制提升高可用；第五，和 Java / Spring Boot 集成成本低；第六，支持 MapStore、监听器、分布式协调等能力；第七，相比本地 HashMap 具备集群能力，相比 Redis 更贴近 JVM 内存状态共享。

因此在撮合系统里，我们用 Hazelcast 做实时状态和高性能读写，用 MySQL 做最终持久化，用 Kafka 做异步解耦，用 Redis 做行情和推送缓存，这样性能、可用性和一致性都能兼顾。
