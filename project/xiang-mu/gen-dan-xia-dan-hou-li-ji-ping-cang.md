# 跟单下单后，立即平仓

会存在这种情况，而且这是跟单系统里比较典型的时序问题。

比如交易员操作很快：

```
T1：交易员开仓
T2：交易员立即平仓
```

但是跟单系统是异步处理的：

```
交易员开仓事件 -> Kafka -> 跟单服务 -> 跟随者下单
交易员平仓事件 -> Kafka -> 跟单服务 -> 跟随者平仓
```

如果跟随者开仓还没执行完成，平仓事件已经到了，就可能出现：

```
跟随者还没有持仓
但是已经收到平仓请求
```

这时候如果直接执行平仓，就会失败，或者出现状态不一致。

标准处理方式一般有几个。

第一，保证同一个交易员、同一个订单链路的消息顺序。

比如 Kafka 里可以用：

```
key = traderId + symbol
```

或者更细一点：

```
key = traderId + masterOrderId
```

这样同一个交易员同一个币对的开仓、平仓事件会进入同一个 Partition，Kafka 可以保证 Partition 内有序。

但是注意，Kafka 有序只能保证事件消费顺序，不能保证跟随者下单一定已经成交完成。因为下单到撮合成交之间还有异步过程。

第二，跟单侧要做状态机控制。

跟随者订单不能只看事件来了就直接执行，而是要维护状态，比如：

```
INIT
OPENING
OPENED
CLOSING
CLOSED
FAILED
```

当收到交易员开仓事件时，跟随者状态进入：

```
OPENING
```

如果这时候又收到平仓事件，不能直接平仓，而是把平仓事件标记为：

```
pendingClose = true
```

等跟随者开仓成功后，再立即执行平仓。

也就是：

```
收到开仓 -> 跟随者下单中
收到平仓 -> 记录待平仓
开仓成功 -> 检查 pendingClose -> 立即平仓
```

第三，如果跟随者开仓失败，平仓请求也不能继续执行。

比如余额不足、风控失败、最小下单量不满足，导致跟随者根本没有开仓成功。那后面的平仓事件应该直接标记为已处理或跳过：

```
开仓失败
收到平仓
检查无持仓
跳过平仓
记录原因
```

第四，要做幂等控制。

开仓事件和平仓事件都可能重复投递，所以要用：

```
masterOrderId
masterTradeId
followerId
eventType
```

生成唯一幂等键，防止重复开仓、重复平仓。

比如：

```
followerId + masterOrderId + OPEN
followerId + masterOrderId + CLOSE
```

第五，平仓时不能只依赖“收到平仓事件”，还要查跟随者真实持仓。

执行平仓前要校验：

```
跟随者是否有对应 symbol 持仓
持仓方向是否一致
持仓数量是否大于 0
是否已经在平仓中
```

如果没有持仓，就不能强行平仓，只能记录为无持仓跳过，或者进入等待状态。

面试标准回答可以这样说：

会存在这种情况。因为跟单系统通常是异步链路，交易员开仓和平仓事件可能很快连续产生，而跟随者下单还要经过风控、余额校验、下单、撮合、成交回报等流程，所以可能出现平仓事件到达时，跟随者开仓还没完成。

解决方式不能简单地收到平仓就直接平仓，而是要通过消息顺序、状态机和幂等来处理。

首先 Kafka 消息要按 traderId + symbol 或 masterOrderId 作为 key，保证同一个交易员同一个币对的事件顺序消费。其次跟单侧要维护跟随者订单状态，比如 OPENING、OPENED、CLOSING、CLOSED。

如果收到开仓事件后跟随者还处于 OPENING 状态，这时又收到平仓事件，就不能立即平仓，而是记录一个 pendingClose 标记。等开仓成功后，系统检查到 pendingClose，再立即触发跟随者平仓。

如果开仓失败，比如余额不足、风控失败或者最小下单量不满足，那么后续平仓事件就直接跳过，并记录原因。

同时开仓和平仓都要做幂等控制，避免消息重复导致重复下单或重复平仓。平仓前还要查询跟随者真实持仓，确认有仓位、方向一致、数量大于 0，才能执行平仓。

所以这类问题本质上是异步系统里的时序一致性问题，核心解决思路是：消息按业务维度保序，跟单状态机控制流程，平仓事件可挂起等待，操作必须幂等，最终以跟随者真实订单和持仓状态为准。
