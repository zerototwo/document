### 项目一：合约小数张数下单全链路改造

第一个项目是 合约小数张数下单全链路改造。\
背景是之前合约交易下单主要是整数张，但业务上需要支持更细粒度的小数张数下单，比如用户可以用更小资金参与合约交易。这个改造不是简单把字段从 int 改成 decimal，因为它涉及交易 API、合约引擎代理、自动单、推送、内部 API 等多个系统。简历里这个项目覆盖了交易 API、合约引擎代理、合约高级自动单、合约消息推送、内部 API 等多个服务。&#x20;

我主要负责的是全链路字段语义、精度校验、接口兼容和多服务联调。核心问题有三个：\
第一是精度问题，比如最小下单量、成交累计量、剩余量，如果还用整数逻辑或者 float 计算，很容易出现比较误差。\
第二是跨系统契约问题，一个服务支持小数了，但下游如果还是按整数解析，就会出现截断、校验失败或者展示不一致。\
第三是存量兼容问题，老客户端、历史订单、老任务都不能因为这次改造受到影响。

我的解决思路是：\
首先，所有数量相关计算统一用 Decimal，不用浮点数，保证下单校验、成交累计、剩余量计算的精度一致。\
其次，我梳理了从入口下单、引擎交互、自动单拆单、成交回写、推送展示、内部查询的完整链路，按依赖顺序分批改造。\
最后，对用户可见的地方，比如推送、展示、统计口径单独验收，避免出现“引擎已经按小数成交，但前端或者推送被截断”的问题。

这个项目最后的结果是，合约系统支持了小数张数下单，同时和整数张行为兼容共存；交易入口、策略执行、推送、内部接口的数量口径也做到了统一，并且通过兼容字段和分阶段发布降低了多系统联动上线风险。&#x20;

这个项目我觉得最能体现我的地方是：我不仅处理了代码改造，还要理解交易业务规则、协调多个服务、控制上线风险，并且保证金融交易系统里最重要的精度和一致性问题。

### 项目二：合约撮合交易系统

项目二你可以这样讲，控制在 3 分钟左右：

***

面试官问：“你讲一个有代表性的项目。”

你可以直接说：

我讲一下我之前做过的 永续合约撮合模块 newex-perpetual-matching。\
这个项目是交易系统里的核心撮合模块，是一个独立部署的 Spring Boot 应用，和 rest 接入层、service 业务层是分离部署的。

它的核心职责是：按合约维护内存订单簿，对用户的下单、撤单、改单进行撮合，撮合完成后产生成交结果，再交给 TradeService 做成交落库、订单状态更新和分布式状态同步，同时异步写 Redis 深度和成交数据，并通过 Pub/Sub 推送行情。

***

然后讲整体架构：

整体架构上，它是一个按合约分片的内存撮合引擎。

系统里有几个核心组件：

第一是 Worker。\
Worker 是一个常驻循环，它会调度各个合约的 Dealer。为了保证同一个合约不会被并发重复撮合，里面用了 runningDealerMap 做控制。只有合约状态正常，并且没有 stop 的情况下，才会调用 dealer.deal()。如果撮合过程中出现异常，会调用 dealer.resetInit()，清空内存订单簿并重新初始化，避免脏状态继续撮合。

第二是 ContractTask。\
它是一个定时任务，大概每 15 秒调用一次 worker.refresh()，用来刷新合约列表、合约分配关系和 dealerMap。

第三是 Dealer。\
Dealer 可以理解为每个合约的撮合执行器。一个合约对应一个 Dealer。Dealer 内部维护 buyDepths 和 sellDepths，也就是买卖盘内存订单簿，底层是 NavigableMap 和 TreeMap，方便按照价格档位排序。初始化时，Dealer 会加载最近成交，并扫描 matchStatus=1 的历史订单恢复订单簿；正式撮合时，会批量拉取 matchStatus=0 的待撮订单，然后进入 realDeal 和 dealOrders 处理。

第四是 Matcher。\
Matcher 是真正执行撮合规则的地方，里面处理下单撮合、撤单、改单。撮合规则包括价格交叉、taker 判定、FOK、价格偏离保护、强平部分成交、爆仓保险金、机器人和普通用户成交策略等。

第五是 TradeServiceImpl。\
撮合完成后，成交结果会交给 TradeServiceImpl 批量处理，包括成交落库、订单状态更新、Hazelcast 分布式状态更新，以及分片订单相关处理。

***

接着讲一次完整流程：

一次完整的撮合流程大概是这样的：

用户在 rest/openapi 下单后，订单先进入待撮合状态。撮合模块不是直接承接用户 REST 流量，而是从待撮订单里批量拉取数据。

ContractTask 定时刷新当前实例负责的合约列表。Worker 根据合约分配结果，为本机负责的合约创建 Dealer。

Dealer 初始化时会把历史未完成订单恢复到内存订单簿。撮合时，Dealer 批量拉取 matchStatus=0 的订单，然后根据订单类型进入 Matcher。

如果是普通下单，就走价格撮合；如果是撤单，就从订单簿里移除；如果是改单，就更新订单价格或数量后重新进入订单簿。

撮合成功以后，系统会生成成交记录和订单状态变更，然后交给 TradeServiceImpl 批量落库，并同步 Hazelcast 中的分布式状态。

最后，深度和成交行情会异步写入 Redis，并通过 Pub/Sub 推送给行情订阅方。

***

然后讲你的设计重点：

这个项目我觉得最核心的设计点有三个。

第一个是单合约串行，多合约并行。\
因为订单簿是强状态结构，同一个合约的买卖盘、价格档位、订单队列、成交顺序必须严格一致。如果同一个合约并发撮合，就需要大量加锁，而且容易出现撤单和成交竞态、订单状态错乱等问题。

所以我们让一个合约集中由一个 Dealer 处理，单合约内部尽量串行，保证价格优先、时间优先和状态一致；不同合约之间通过 Worker 调度多个 Dealer，可以并行处理，提升整体吞吐。

第二个是撮合主链路内存化。\
订单簿维护在内存里，撮合时不需要每笔订单都查数据库。数据库更多承担最终持久化和状态恢复作用。这样可以减少数据库 IO，让撮合链路更短。

第三个是非核心链路异步化。\
像 Redis 深度写入、成交行情推送、Pub/Sub 这些，不阻塞撮合主流程，而是通过异步方式处理。这样可以避免行情推送或缓存写入影响撮合性能。

***

再讲高可用：

高可用方面，这个系统主要依赖 Nacos 做服务发现和合约分片。

CoinDistributionServiceImpl 会从 Nacos 获取当前所有撮合实例，然后通过一致性哈希和虚拟节点，把合约分配到不同实例上。每台机器只负责一部分合约，分片结果会写到 Nacos metadata 里。Worker 只会对本机负责的合约创建 Dealer。

当实例上线或下线时，InstanceChangeNotifier 会监听 Nacos 实例变化，并刷新本机 metadata 中的合约配置。这样其他实例可以接管下线机器负责的合约。

下线时，系统里也有 NacosServiceUnregister 和 ShutdownHookInitializer，会先从注册中心注销，并停止撮合循环，避免实例退出过程中还继续撮合。

另外，启动时还有 tryLockSocket 绑定固定端口，防止单机误启动两个撮合进程，导致同一台机器上跑出两套撮合服务。

***

讲项目难点：

这个项目的难点主要有几个。

第一是订单簿一致性。\
撮合、撤单、改单都可能修改订单簿，如果并发控制不好，很容易出现订单重复成交、已经撤单又成交、改单后价格档位错误等问题。所以我们用单合约 Dealer 集中处理，减少并发修改订单簿的风险。

第二是故障恢复。\
因为订单簿在内存里，服务重启后必须能恢复。Dealer 初始化时会加载最近成交和历史未完成订单，把订单簿恢复出来；异常时 resetInit 重新初始化，避免脏数据继续参与撮合。

第三是合约分片与实例变更。\
多实例部署时，不能出现多个实例同时撮合同一个合约，也不能出现合约没人处理。所以通过 Nacos 实例列表、一致性哈希和 metadata 来维护本机负责的合约范围。

第四是性能和一致性的平衡。\
撮合要快，但不能为了快破坏订单状态一致性。所以我们把撮合主逻辑放在内存中执行，同时将落库、行情推送这些链路批量化、异步化。

***

最后总结：

总结一下，这个项目本质上就是一个 按合约分片的内存撮合引擎。

它通过 Dealer 维护单合约订单簿，通过 Matcher 完成下单、撤单、改单撮合规则，通过 TradeServiceImpl 批量落库并更新 Hazelcast 分布式状态，通过 Redis 异步输出深度和成交行情，通过 Nacos 做合约分片、服务发现和实例变更处理。

我觉得这个项目比较有代表性，是因为它不是普通业务 CRUD，而是交易系统核心链路，涉及内存订单簿、价格时间优先、单合约串行、多合约并行、分布式分片、高可用、异步推送和状态一致性。

这个项目也让我对交易系统里性能、正确性和高可用之间的平衡有了比较深入的理解。
