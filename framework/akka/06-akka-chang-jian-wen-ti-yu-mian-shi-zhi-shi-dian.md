# 06 · Akka 常见问题与面试知识点

### 1. Akka 是什么

Akka 是基于 Actor 模型的并发框架。

应用可以拆成多个 Actor，每个 Actor 通过消息与其他 Actor 交互，并管理自己的状态。

面试时可以这样回答：

> Akka 将并发业务组织为 Actor。每个 Actor 串行处理自己的普通消息，不同 Actor 可以并行执行。它提供消息通信、生命周期管理和异常监督等能力，适合需要独立状态和任务协作的场景。

这里的“串行处理”不意味着 Actor 启动的外部异步任务也串行完成。

### 2. ActorSystem、Actor、ActorRef 有什么区别

| 概念          | 职责                         |
| ----------- | -------------------------- |
| ActorSystem | 提供运行环境，管理 Actor、调度及生命周期等资源 |
| Actor       | 处理消息，管理自身状态                |
| ActorRef    | 指向 Actor 的通信引用             |
| Props       | 描述如何创建 Actor 实例            |

对应代码：

```
ActorSystem system = ActorSystem.create("demo");

ActorRef worker = system.actorOf(
        Props.create(Worker.class),
        "worker"
);
```

可以这样解释：

> ActorSystem 根据 Props 创建并管理 Actor，返回 ActorRef。调用方通过 ActorRef 发消息，不直接调用 Actor 实例的业务方法。

### 3. 一个 Actor 对应一个线程吗

**不对应。**

Actor 通常由 Dispatcher 的线程池调度。同一个 Actor 处理不同消息时，可能使用不同线程。

```
线程池
├── 线程 1：处理 Actor A 的消息
├── 线程 2：处理 Actor B 的消息
└── 线程 3：处理 Actor C 的消息
```

需要记住：

* 同一个 Actor 一次处理一条普通消息。
* 不同 Actor 可以并行处理消息。
* Actor 数量不等于线程数量。

因此，不能通过创建更多 Actor，直接推导出业务处理能力一定提高。

### 4. Actor 内的字段为什么通常不需要加锁

前面的 Counter 使用：

```
private int total;
```

累加逻辑：

```
.match(Add.class, message -> {
    total += message.amount();
})
```

如果这个字段只在当前 Actor 的消息处理逻辑中访问，不会有两个消息处理函数同时修改它，因此通常不需要锁或 `AtomicInteger`。

但以下情况不能直接套用这个结论：

```
多个 Actor 修改同一个共享 Map
外部线程直接修改 Actor 持有的对象
异步回调直接修改 Actor 字段
```

面试时可以这样回答：

> Actor 的串行处理可以保护由它独占管理的状态，但不会自动保护外部共享对象，也不会约束外部异步回调线程。

### 5. tell 是同步还是异步

`tell()` 是异步发送：

```
receiver.tell(message, sender);
```

| 内容       | 含义         |
| -------- | ---------- |
| receiver | 接收者        |
| message  | 消息         |
| sender   | 这条消息声明的发送者 |

`tell()` 返回不代表业务已经完成，也不提供业务成功结果。

```
worker.tell(Command.START, getSelf());

System.out.println("发送方法已返回");
```

打印日志时，Worker 可能尚未开始，也可能已经处理完成。

### 6. Actor 如何回复消息

接收方处理消息时，可以通过 `getSender()` 回复：

```
getSender().tell(
        new Value(total),
        getSelf()
);
```

这表示：

```
接收者：当前消息的发送者
消息：Value
发送者：当前 Actor
```

回复仍然是一条异步消息，不是普通方法的 `return`。

`getSender()` 与当前处理的消息有关，不能将它理解为永远固定的调用方。

### 7. tell 和 ask 有什么区别

| 对比项       | tell  | ask                            |
| --------- | ----- | ------------------------------ |
| 主要用途      | 发送消息  | 请求一个回复                         |
| 返回业务结果    | 不直接返回 | 通过 Future 或 CompletionStage 接收 |
| 等待回复超时    | 自行设计  | 通常需要指定超时                       |
| 调用方是否必须阻塞 | 不需要   | 也不需要                           |

`ask` 本身也是异步的。

如果调用方在返回的 Future 上执行阻塞等待，才会把自己的执行流程阻塞住。

#### ask 超时意味着什么

它只表示规定时间内没有收到所期待的回复。

可能的原因包括：

* 请求仍在邮箱中等待。
* 接收方处理比较慢。
* 接收方没有回复。
* 请求或回复未能送达。

**超时不代表业务已经取消，也不代表业务一定没有执行成功。**

超时后重试扣款、下单等操作，需要考虑幂等。

### 8. Akka 能保证消息顺序吗

需要说明适用范围。

在前面的 Demo 中，同一个 Teacher 直接向同一个 Counter 发送：

```
counter.tell(new Add(1), getSelf());
counter.tell(new Add(2), getSelf());
counter.tell(GetValue.INSTANCE, getSelf());
```

使用默认邮箱时，Counter 按上述顺序处理。

但没有跨发送者的全局顺序保证：

```
Teacher A → Counter：Add(1)
Teacher B → Counter：GetValue
```

不能仅凭两个发送方各自的代码，推断 Counter 一定先累加再查询。

此外：

* 自定义优先级邮箱可能改变处理顺序。
* 经过中间 Actor 转发的链路，不能直接套用原发送者的顺序关系。
* 消息处理顺序不等于外部异步操作完成顺序。

面试回答应同时说明：**顺序保证不等于消息一定送达。**

### 9. 普通消息传递可靠吗

Akka 普通消息传递提供的是 **at-most-once，至多一次投递语义**。

它不承诺消息必达，也不承诺业务一定成功。普通发送机制不会因为缺少业务确认而自动重试。

如果业务需要可靠处理，通常还需要设计：

```
请求标识
    ↓
接收与处理
    ↓
业务确认
    ↓
超时重试
    ↓
幂等去重
```

内存邮箱也不是持久化消息队列，进程退出后不会自动恢复其中的待处理消息。

### 10. 消息积压怎么办

Actor 处理能力有限。如果发送速度长期高于处理速度，邮箱会积压。

```
发送速度：每秒 1000 条
处理速度：每秒 100 条
    ↓
等待处理的消息持续增加
```

排查时先区分：

| 原因                | 处理思路         |
| ----------------- | ------------ |
| 单条处理耗时过长          | 优化逻辑，检查阻塞调用  |
| 单个 Actor 承担过多独立工作 | 按业务键拆分 Actor |
| 上游发送不受控           | 限流或增加确认协议    |
| 大量消息已过期           | 设计合并、丢弃或版本判断 |
| 邮箱缺少容量限制          | 评估有界邮箱及溢出处理  |

有界邮箱可以限制积压规模，但**不会自动形成完整的背压协议**。业务仍需决定容量不足时如何反馈和处理。

需要流式背压时，可以评估 Akka Streams。

### 11. 可以在 Actor 中执行阻塞操作吗

技术上可以，但可能占用共享 Dispatcher 的线程，影响其他 Actor。

例如：

```
Thread.sleep(5000);
```

或者同步等待网络、数据库响应。

常见处理方向：

* 使用异步 I/O。
* 将必须阻塞的工作隔离到专用 Dispatcher。
* 控制同时执行的任务数量。
* 将执行结果作为消息发送回 Actor。

不要在 Actor 内阻塞等待另一个 Actor 的回复。

### 12. 异步结果应该怎么处理

推荐流程：

```
Actor 收到请求
    ↓
启动异步任务
    ↓
异步任务完成
    ↓
将结果发送回 Actor
    ↓
Actor 处理结果消息，更新状态
```

不应在外部回调线程里直接修改 Actor 的内部字段。

还要考虑结果过期：

```
请求 A 发出
请求 B 发出
结果 B 先返回
结果 A 后返回
```

如果直接覆盖状态，较旧的 A 可能覆盖较新的 B。可以根据业务使用请求编号或版本判断结果是否仍然有效。

在回调需要回复原请求者时，应在处理原消息期间保存对应的 ActorRef，不要在回调中重新调用 `getSender()` 获取它。

### 13. restart 和 resume 有什么区别

| 内容            | restart | resume |
| ------------- | ------- | ------ |
| Java Actor 实例 | 重建      | 保留     |
| 普通实例字段        | 重新初始化   | 保留当前值  |
| ActorRef      | 保持有效    | 保持有效   |
| 失败消息自动重试      | 不会      | 不会     |

前面的 Worker 故障前：

```
count = 1
```

使用 restart：

```
新实例，count = 0
```

使用 resume：

```
原实例，count = 1
```

如果消息抛异常之前已经部分修改了状态，resume 会保留这些修改。选择策略时需要考虑状态是否仍然有效。

### 14. Actor 重启会恢复业务状态吗

普通 restart 不会自动恢复内存中的业务状态。

```
private int count;
```

新实例创建后，`count` 重新初始化为 0。

如果需要恢复，可以根据业务从数据库加载，或使用 Akka Persistence 等机制。

需要区分：

```
恢复 Actor 的业务状态
≠
恢复所有尚未处理的邮箱消息
≠
回滚外部副作用
```

Actor 持久化也不能直接替代跨系统事务设计。

### 15. watch 和监督有什么区别

| 机制    | 作用                |
| ----- | ----------------- |
| 监督策略  | 决定子 Actor 失败后如何处理 |
| watch | 订阅某个 Actor 的终止通知  |

```
getContext().watch(worker);
```

Worker 真正停止后，观察者收到 `Terminated`。

普通 restart 不产生 `Terminated`。

监督来自父子关系；`watch()` 可以观察非子 Actor。

### 16. 定时器是在直接调用业务方法吗

不是。

Actor 自带定时器的执行流程是：

```
定时器发送 Tick
    ↓
进入 Actor 邮箱
    ↓
Actor 处理 Tick
    ↓
执行业务
```

因此：

* Tick 可能在邮箱中等待。
* 同一 Actor 不会并发执行两个普通消息处理函数。
* 定时发送的间隔不等于业务完成后的等待间隔。

如果要求每轮完成后再等待一秒，应在完成时安排下一次单次定时消息。

### 17. 重启后会不会出现多个定时任务

取决于定时器的使用方式。

#### Actor 自带 Timer

使用 `AbstractActorWithTimers`：

```
getTimers().startTimerWithFixedDelay(...);
```

定时器与 Actor 生命周期绑定，停止或重启时会自动取消。

#### 系统 scheduler

使用：

```
ActorSystem.scheduler() + Cancellable
```

需要自行管理取消动作。

如果旧任务未取消，而新实例启动时又注册任务，可能出现多个调度任务持续发送消息。

### 18. Akka 和线程池有什么区别

| 对比项     | 线程池        | Actor         |
| ------- | ---------- | ------------- |
| 核心对象    | 待执行任务      | 有身份和状态的工作单元   |
| 通信方式    | 提交任务、共享数据等 | 发送消息          |
| 状态管理    | 开发者自行组织    | 可由 Actor 独占管理 |
| 生命周期与监督 | 通常自行实现     | 框架提供相关机制      |
| 执行资源    | 管理工作线程     | 通常仍依赖线程池调度    |

可以这样回答：

> Actor 提供了组织并发业务的模型，线程池提供任务执行资源。两者并不是互相替代的关系，Akka 通常也使用线程池调度 Actor。

### 19. Akka 和 @Scheduled 怎么选择

只有一个简单的定时任务时，`@Scheduled` 通常更直接。

当任务还需要以下能力时，可以考虑 Actor：

* 持续维护独立状态。
* 接收暂停、恢复、查询等消息。
* 与其他 Actor 协作。
* 通过父子关系管理生命周期和故障。

选择依据是业务协作和状态管理需求，不是“用了 Akka 就一定更快”。

### 20. 面试中如何介绍这组 Demo

可以按以下顺序表达：

> 我使用 Akka Classic 编写了四个学习案例。第一个理解 ActorSystem、ActorRef 和异步消息；第二个通过两个 Counter 理解状态隔离、消息顺序和回复；第三个通过 Monitor 理解定时消息与生命周期；第四个通过 Parent 和 Worker 观察异常监督、重启和停止。
>
> 其中最关键的认识是：Actor 串行处理只覆盖自身消息处理过程，tell 返回不代表业务完成，重启也不等于业务重试或状态恢复。

如果这些是学习 Demo，应明确说明，不将其描述为未经实践的生产经验。
