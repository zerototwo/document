# 01 · Disruptor 是什么与核心概念

### 1. Disruptor 是什么

Disruptor 是一个用于**单个进程内、线程之间传递事件**的高性能 Java 库。

它可以让生产线程和消费线程分工：

```
生产线程
    ↓ 发布事件
RingBuffer
    ↓ 读取事件
消费线程
    ↓
执行业务
```

例如：

```
接收订单 → 发布订单事件 → 消费者计算 → 输出结果
```

它不是 Kafka、RabbitMQ 这样的消息中间件，不提供跨进程消息存储和投递服务。

本系列使用 **Java 17、Disruptor 3.4.4**。后面的工作池 Demo 使用该版本的 API，不同大版本不能直接混用。

### 2. 为什么需要生产者和消费者

假设接收请求时，还需要进行计算：

```
接收请求 → 计算 → 接收下一条请求
```

如果接收与计算都在同一个线程中，计算耗时会影响继续接收。

通过生产者与消费者分工：

```
生产线程：接收 → 发布 → 接收 → 发布
                    ↓
                 缓冲区
                    ↓
消费线程：       读取 → 计算
```

缓冲区可以吸收短时间的速度差异。

但如果生产速度长期超过消费速度，缓冲区最终仍会填满。Disruptor 不会自动解决业务处理能力不足的问题。

### 3. RingBuffer：环形缓冲区

RingBuffer 是预先分配的一组事件槽位，使用时循环访问。

假设容量为 4：

```
槽位：    0       1       2       3
       [事件]  [事件]  [事件]  [事件]
          ↑                     │
          └───── 循环使用 ───────┘
```

发布的事件数量可以超过 4，但不能随意覆盖消费者尚未处理完的数据。

容量需要是 2 的幂，例如：

```
4、8、16、1024、65536
```

固定容量让内存占用更可控，但容量大小仍需结合事件大小、流量和允许的积压时间选择。

### 4. Event：槽位中存放的对象

事件对象用来承载业务数据，例如：

```
public static class NumberEvent {
    private long value;

    public long getValue() {
        return value;
    }

    public void setValue(long value) {
        this.value = value;
    }
}
```

RingBuffer 初始化时，会通过事件工厂为各个槽位创建对象：

```
NumberEvent::new
```

如果容量为 4，可以理解为预先创建了 4 个 `NumberEvent` 对象。

后续发布时，通常修改已有对象中的字段，而不是每次都创建新的事件外壳。

#### 对象复用需要注意什么

一个槽位可能先承载数字 10，之后被复用来承载数字 20。

因此，消费者不能长期保存这个事件对象的引用，并假设它的内容不会再变化。

如果需要把数据交给异步任务，应提取必要字段，或创建独立的数据快照。

对象复用也不意味着业务完全不产生垃圾。例如，每次向字段放入一个新对象，仍然会发生分配。

### 5. Sequence：事件序号

RingBuffer 的槽位会循环使用，但事件序号持续递增。

假设容量为 4：

| 事件序号 Sequence | 对应槽位 |
| ------------- | ---- |
| 0             | 0    |
| 1             | 1    |
| 2             | 2    |
| 3             | 3    |
| 4             | 0    |
| 5             | 1    |

可以用下面的关系理解：

```
槽位下标 = sequence & (容量 - 1)
```

需要区分：

* **槽位**是可复用的存储位置。
* **Sequence**标识这一次发布所处的位置。
* **消费者序号**记录消费者已经处理到哪里。

序号机制帮助生产者判断槽位能否复用，也帮助消费者判断哪些事件可以读取。

### 6. Producer：生产者

生产者负责取得可用位置、写入数据并发布。

典型代码：

```
long sequence = ringBuffer.next();

try {
    NumberEvent event = ringBuffer.get(sequence);
    event.setValue(100);
} finally {
    ringBuffer.publish(sequence);
}
```

这段代码分成三个步骤：

```
申请序号 → 填充事件 → 发布序号
```

#### next()

```
long sequence = ringBuffer.next();
```

申请一个可以写入的位置。

如果 RingBuffer 已满，无法安全复用下一槽位，调用可能等待消费者推进。

#### get(sequence)

```
NumberEvent event = ringBuffer.get(sequence);
```

取得对应槽位中预先创建的对象。

#### publish(sequence)

```
ringBuffer.publish(sequence);
```

将填充好的事件发布出去，让消费者能够按序处理。

申请序号不等于已经发布。消费者不能仅凭生产者申请了位置，就读取尚未写好的数据。

示例使用 `finally` 避免申请后遗漏发布。实际业务还应尽量在申请前完成可能失败的校验和计算，防止异常时发布半成品或残留数据。

### 7. Consumer：消费者

最常见的消费者处理接口是 `EventHandler`：

```
EventHandler<NumberEvent> handler =
        (event, sequence, endOfBatch) -> {
            System.out.println(event.getValue());
        };
```

三个参数分别是：

| 参数           | 含义              |
| ------------ | --------------- |
| `event`      | 当前序号对应的事件对象     |
| `sequence`   | 当前事件序号          |
| `endOfBatch` | 是否为本次可处理批次的最后一条 |

`endOfBatch = true` 不表示生产者以后不会再发布事件，也不表示整个程序处理结束。

使用标准 `EventHandler` 配置时，每个对应的事件处理器按序调用自己的 handler。不同消费者之间如何并行或等待，取决于配置的依赖关系。

### 8. 多个消费者如何分工

多个消费者并不天然意味着“每人分到一部分”。

#### 广播消费

```
disruptor.handleEventsWith(handlerA, handlerB);
```

表示两个消费者各自处理全部事件。

```
              ┌── Handler A：处理全部事件
RingBuffer ───┤
              └── Handler B：处理全部事件
```

发布 6 条事件时，A 和 B 各执行 6 次。

#### 依赖消费

```
disruptor.handleEventsWith(calculate).then(output);
```

表示 `output` 需要等待 `calculate` 完成对应序号的处理。

```
事件 → calculate → output
```

不同阶段可以对不同事件形成流水线，不要求先计算完全部事件再统一输出。

#### 工作池消费

Disruptor 3.4.4 提供：

```
disruptor.handleEventsWithWorkerPool(workerA, workerB);
```

同一个工作池中，一条事件由其中一个 worker 处理，不是每个 worker 都处理一遍。

后续 Demo 会分别演示这些区别。

### 9. ProducerType：单生产者和多生产者

创建 Disruptor 时，需要根据发布线程的情况选择：

```
ProducerType.SINGLE
```

或：

```
ProducerType.MULTI
```

| 配置       | 使用条件                        |
| -------- | --------------------------- |
| `SINGLE` | 只有一个线程向该 RingBuffer 发布事件    |
| `MULTI`  | 可能有多个线程向该 RingBuffer 并发发布事件 |

这里描述的是**生产线程数量**，不是消费者数量，也不是事件类型数量。

即使只有一个 Service 对象，如果多个请求线程都会调用它发布事件，也需要考虑使用 `MULTI`。

### 10. WaitStrategy：消费者等待策略

没有新事件时，消费线程需要等待。

WaitStrategy 决定如何等待：

| 策略                     | 特点                   |
| ---------------------- | -------------------- |
| `BlockingWaitStrategy` | 使用阻塞等待，通常适合作为入门配置    |
| `SleepingWaitStrategy` | 分阶段自旋、让出执行机会和短暂休眠    |
| `YieldingWaitStrategy` | 自旋并让出执行机会，可能消耗较多 CPU |
| `BusySpinWaitStrategy` | 持续自旋，对 CPU 资源要求较高    |

不能简单认为越消耗 CPU 就一定越适合业务。效果取决于可用核心、负载和延迟目标，需要实测。

WaitStrategy 主要控制消费者等待事件的行为，不应将它理解为缓冲区满时生产者的统一等待配置。

### 11. Disruptor 为什么可能更高效

它通过以下设计降低线程间传递事件的开销：

* 预分配并复用事件对象，减少部分对象分配。
* 使用固定大小的环形数组。
* 通过序号协调发布、消费和槽位复用。
* 支持批量处理和不同等待策略。
* 对关键并发数据进行缓存行布局优化，减少伪共享影响。

这些设计不保证所有场景都比普通队列快。如果主要耗时在数据库、网络或业务计算，替换传递机制未必能明显改善整体性能。

### 12. Disruptor 不提供什么

| 能力           | 是否自动提供 |
| ------------ | ------ |
| 进程内事件传递      | 是      |
| 消费者依赖关系      | 是      |
| 消息持久化        | 否      |
| 跨进程消息传输      | 否      |
| 业务失败自动重试     | 否      |
| 数据库事务        | 否      |
| 进程崩溃后恢复待处理事件 | 否      |

异常处理、重试、幂等和状态恢复，需要根据业务单独设计。
