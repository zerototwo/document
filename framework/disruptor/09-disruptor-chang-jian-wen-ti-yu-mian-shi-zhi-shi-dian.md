# 09 · Disruptor 常见问题与面试知识点

### 1. Disruptor 是什么

Disruptor 是用于单个进程内、线程之间传递事件的高性能 Java 库。

核心流程：

```
生产者 → RingBuffer → 消费者
```

面试时可以这样回答：

> Disruptor 使用预分配的环形缓冲区承载事件，通过序号协调生产、消费和槽位复用，支持多个消费者之间的并行与依赖关系。它主要解决进程内事件传递问题，不是提供持久化和跨进程通信的消息中间件。

本系列 Demo 使用 **Disruptor 3.4.4**。其中工作池 API 在 4.x 中已移除，讨论具体 API 时需要说明版本。

### 2. RingBuffer 是什么

RingBuffer 是固定容量、循环使用的事件存储结构。

假设容量为 4：

```
sequence：0  1  2  3  4  5
槽位下标：0  1  2  3  0  1
```

序号持续递增，槽位循环使用。

循环使用不意味着任意覆盖。生产者必须等待相关消费者的进度允许，才能复用对应槽位。

### 3. 为什么容量必须是 2 的幂

Disruptor 使用位运算计算槽位下标：

```
sequence & (bufferSize - 1)
```

容量为 2 的幂时，可以通过这种方式将序号映射到环形数组。

合法容量例如：

```
4、8、16、1024
```

但容量不是越大越好：

* 更大容量可以吸收更大的瞬时积压。
* 会增加预分配内存占用。
* 无法解决长期生产速度高于消费速度的问题。
* 积压更多事件，也可能意味着更高的等待延迟。

### 4. Disruptor 为什么可能更快

主要设计包括：

| 设计      | 作用                 |
| ------- | ------------------ |
| 环形数组    | 固定存储结构，减少节点管理开销    |
| 预分配事件对象 | 减少事件外壳的重复分配        |
| 序号协调    | 管理并发发布、消费进度和槽位复用   |
| 批量处理    | 分摊部分协调开销           |
| 缓存行布局优化 | 减少关键计数器之间的伪共享      |
| 可选等待策略  | 根据 CPU 和延迟目标选择等待方式 |

面试时不要直接说“Disruptor 一定比阻塞队列快”。

如果业务主要耗时在数据库或网络，传递机制的优化可能只占整体耗时的一小部分，需要实测。

### 5. 什么是伪共享

两个线程修改不同变量，但变量位于同一个 CPU 缓存行中，可能导致缓存行反复失效和同步。

```
同一缓存行
├── 线程 A 修改的变量
└── 线程 B 修改的变量
```

虽然它们没有修改同一个变量，仍然可能相互影响性能，这就是伪共享。

Disruptor 对关键序号等结构进行缓存行布局优化，以降低这种影响。它不会自动消除所有业务对象中的伪共享。

### 6. 发布事件为什么分成三个步骤

```
long sequence = ringBuffer.next();

try {
    NumberEvent event = ringBuffer.get(sequence);
    event.setValue(value);
} finally {
    ringBuffer.publish(sequence);
}
```

对应：

```
申请位置 → 填充数据 → 发布
```

| 操作                  | 含义               |
| ------------------- | ---------------- |
| `next()`            | 申请可写位置，容量不足时可能等待 |
| `get(sequence)`     | 取得槽位中的已有对象       |
| `publish(sequence)` | 标记该序号已经准备好       |

申请位置不代表数据已经写完，消费者不能读取尚未发布的事件。

### 7. 为什么 publish 放在 finally 中

申请序号后，如果遗漏发布，可能留下未发布的位置，阻碍消费推进。

但 `finally` 只能帮助确保发布动作执行，不能保证事件有效。

如果填充时发生异常，仍可能发布不完整的数据。

实际业务应尽量：

```
先校验和计算
    ↓
再申请位置
    ↓
快速填充完整字段
    ↓
发布
```

如果业务允许失败事件进入流程，应使用明确的状态表达失败，避免消费者误读旧数据。

### 8. 对象复用有什么风险

RingBuffer 中的事件对象可能先承载事件 A，之后承载事件 B。

因此：

* 发布时要完整设置本次事件字段。
* 生产者发布后不要继续修改事件。
* 消费者不要长期保存槽位对象的引用。
* 异步处理应提取字段或创建独立快照。

例如：

```
保存 event 引用到异步任务
    ↓
消费回调返回，进度推进
    ↓
槽位被复用
    ↓
异步任务读到下一次事件的数据
```

复用事件外壳也不等于零 GC。字段中创建的新字符串、集合和其他业务对象仍可能产生分配。

### 9. SINGLE 和 MULTI 怎么选择

| 模式       | 使用条件        |
| -------- | ----------- |
| `SINGLE` | 只有一个线程发布    |
| `MULTI`  | 可能有多个线程并发发布 |

判断对象是**发布线程数量**，不是消费者数量，也不是 Service 实例数量。

多个请求线程调用同一个 Service 发布事件，仍然属于多生产者场景。

`MULTI` 协调 RingBuffer 的发布过程，不会自动保护生产者操作的其他共享业务对象。

### 10. 多生产者如何避免写入冲突

多生产者模式通过原子操作等机制协调序号申请，并记录各序号的发布状态。

每个生产者只能填充自己申请到的位置。

如果：

```
生产者 A：申请序号 0，尚未发布
生产者 B：申请序号 1，已经发布
```

标准消费者不会跳过序号 0，直接处理序号 1。它需要等待连续可用的事件。

所以某个生产者申请后长时间不发布，也可能阻碍后续消费。

### 11. RingBuffer 满了怎么办

`next()` 可能等待，直到消费者推进到允许复用槽位的位置。

```
生产速度持续高于消费速度
    ↓
缓冲区填满
    ↓
生产者等待
```

不希望因容量不足而等待时，可以使用 `tryNext()`，并处理 `InsufficientCapacityException`。

容量不足后的策略由业务决定，例如拒绝、限流或稍后重试。不能把“捕获异常后忽略”当成所有业务都能接受的处理方式。

### 12. WaitStrategy 控制谁等待

主要控制**消费者等待新事件**的方式。

| 策略                     | 特点                 |
| ---------------------- | ------------------ |
| `BlockingWaitStrategy` | 使用阻塞等待，空闲时通常较省 CPU |
| `SleepingWaitStrategy` | 分阶段自旋、让出执行机会和短暂休眠  |
| `YieldingWaitStrategy` | 自旋并让出执行机会，可能较耗 CPU |
| `BusySpinWaitStrategy` | 持续自旋，需要充足 CPU 资源   |

不要将它与生产者容量不足时的等待混淆。

选择策略应结合核心数量、负载和延迟目标。业务处理慢时，改用忙等不会自动提升业务计算速度。

### 13. EventHandler 和 WorkHandler 有什么区别

针对本系列使用的 3.4.4：

| 对比项         | EventHandler         | WorkHandler                    |
| ----------- | -------------------- | ------------------------------ |
| 配置方式        | `handleEventsWith()` | `handleEventsWithWorkerPool()` |
| 同组中一条事件由谁处理 | 每个 handler 都处理       | 其中一个 worker 处理                 |
| 典型用途        | 多个不同职责各处理一遍          | 多个 worker 分担相同工作               |

广播模式：

```
disruptor.handleEventsWith(handlerA, handlerB);
```

发布 6 条，A 和 B 各处理 6 条。

工作池模式：

```
disruptor.handleEventsWithWorkerPool(workerA, workerB);
```

正常执行时，两者合计处理 6 条，不保证平均分配。

“一条事件分给一个 worker”不等于端到端业务 exactly-once。

### 14. 工作池能保证完成顺序吗

不能。

```
事件 1 → Worker A，耗时 500ms
事件 2 → Worker B，耗时 10ms
```

事件 2 可能先完成。

序号分配有顺序，不代表并行任务按同样顺序完成。

如果同一账户的事件需要串行处理，可以考虑按账户分片，每个分片使用一个串行处理阶段。

### 15. then 的作用是什么

```
disruptor.handleEventsWith(calculate).then(output);
```

建立消费者依赖：

```
calculate → output
```

output 等待 calculate 的消费进度达到对应序号，才能处理该事件。

对于正常同步完成的回调，下游能读取上游完成前写入的数据。

但它不表示：

* 所有事件计算完后才开始输出。
* 上下游在同一个线程执行。
* 自动等待上游启动的外部异步任务。
* 上游业务一定成功。

如果上游异常被记录后跳过，下游仍可能处理到该事件，需要业务状态配合判断。

### 16. endOfBatch 是什么

`endOfBatch` 表示当前事件是否为本次可处理批次的最后一条。

```
本批次：0、1、2
             ↑
       endOfBatch=true
```

它不表示：

```
生产结束
所有事件处理完成
之后不会再有数据
```

批次边界受运行时发布和调度影响，不应假设它固定出现在哪个业务数字上。

### 17. 消费者抛异常后，会自动重试吗

不会。

在前面的异常 Demo 中，数字 3 抛异常，异常处理器记录错误后正常返回：

```
1、2 成功
3 失败，被跳过
4、5 继续处理
```

对于该标准事件处理器，这种配置允许消费进度继续推进，但没有重试数字 3。

如果异常处理器再次抛异常，消费处理器可能退出。

需要业务重试时，应另外设计失败数据快照、重试次数、幂等以及必要的持久化。

### 18. shutdown 正常返回意味着什么

它表示消费进度已经追上已发布事件，并请求停止处理器。

不意味着所有业务都成功。

例如：

```
发布 5 条
成功 4 条
失败 1 条，异常处理器返回后跳过
```

消费进度仍可以追上，`shutdown()` 可以正常返回。

正确关闭通常应先停止发布，再等待消费。如果生产者还持续发布，关闭等待可能无法按预期结束。

### 19. shutdown 和 halt 有什么区别

| 方法                | 作用              |
| ----------------- | --------------- |
| `shutdown()`      | 等待消费进度追上后停止处理器  |
| 带超时的 `shutdown()` | 限制等待时间，超时抛异常    |
| `halt()`          | 请求停止处理器，不保证排空事件 |

`halt()` 不会强制中断正在运行的业务函数，也不会回滚副作用。

如果业务回调永久阻塞，单纯调用 `halt()` 不代表线程立即结束。

### 20. 按账户分片能保证什么

固定分片数和路由规则：

```
int shardId = Math.floorMod(accountId, shardCount);
```

让同一账户进入同一 RingBuffer，并由单个同步消费者处理，可以保证沿该路径串行执行。

但它不能自动保证：

* 上游乱序事件被恢复为业务顺序。
* 外部异步任务按序完成。
* 不同账户一定分到不同分片。
* 跨账户事务原子性。
* 动态改变分片数时状态和顺序不受影响。

增加分片前，需要考虑路由变化、在途事件和状态迁移。

### 21. Disruptor 与 BlockingQueue 怎么选择

| 对比项    | BlockingQueue | Disruptor        |
| ------ | ------------- | ---------------- |
| 使用复杂度  | 通常更直接         | 需要理解序号、复用和消费拓扑   |
| 数据结构   | 取决于实现，可为数组或链表 | 固定环形数组           |
| 事件对象复用 | 通常由业务自行设计     | 提供预分配槽位模式        |
| 消费者依赖链 | 通常自行组织        | DSL 支持           |
| 合适场景   | 常规任务交接        | 对延迟、吞吐和处理拓扑有明确要求 |

选择 Disruptor 应有实际需求和测量依据。不能仅凭“无锁”“高性能”等标签作决定；例如阻塞等待策略本身也会使用锁和条件等待。

### 22. 面试中如何介绍这组 Demo

可以这样表达：

> 我用七个 Demo 学习了 Disruptor。先通过基础生产消费理解 RingBuffer 和序号，再通过慢消费者观察容量约束，通过多生产者理解 SINGLE 与 MULTI。随后对比广播和工作池，使用 then 配置计算与输出的依赖，最后验证异常跳过、关闭语义和按账户分片。
>
> 我重点理解了几个边界：事件对象会复用，发布顺序不等于并行业务完成顺序，消费进度追上不等于业务全部成功，分片也不会自动修复上游乱序。

如果只是学习案例，应明确说明，不将其描述成生产项目经验。
